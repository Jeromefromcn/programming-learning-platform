## 1. Missing Blocks

### Problem
`AVAILABLE_BLOCKS` in `BlocklyAuthoringWorkspace.jsx` contains 23 blocks. Blockly's installed `blocks_compressed.js` provides significantly more. Tutors cannot enable commonly needed blocks such as `controls_forEach`, `math_modulo`, `math_round`, or the keyboard input block `text_prompt_ext`.

### Solution
Add all missing functionally useful blocks to `AVAILABLE_BLOCKS`. Each entry keeps the existing shape `{ type, label, category }`.

## 2. Keyboard Input Support

### Problem
`text_prompt_ext` calls `window.prompt()`. The current worker stubs `prompt` to always return `''`, so input blocks produce no real input.

### Modes
Two modes compose as a single fallback pipeline — no mode toggle:
1. **Pre-defined inputs** — student fills a textarea (one value per line) before clicking Run. Values are consumed in order.
2. **Interactive modal** — when pre-defined inputs are exhausted (or none were provided) and code calls `prompt()`, a modal appears mid-execution asking for a value.

### Technical Mechanism — SharedArrayBuffer + Atomics

Web Workers cannot be paused with ordinary async messaging. The interactive modal requires the worker thread to truly block until the main thread provides a value. This is achieved via `SharedArrayBuffer` and `Atomics.wait()`.

**Prerequisite:** The Nginx server must send:
```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```
These headers enable `SharedArrayBuffer` in the browser. They are safe for this single-origin deployment (no cross-origin iframes or scripts).

**SharedArrayBuffer layout (1028 bytes total):**

| Bytes | Type | Meaning |
|---|---|---|
| 0–3 | Int32 | State: `0` = idle / waiting, `1` = response ready |
| 4–7 | Int32 | Response byte length |
| 8–1027 | Uint8[1020] | Response UTF-8 bytes (max 1020 chars) |

The prompt message text (shown in the modal) travels via `postMessage` from the worker to the main thread — it does not occupy space in the SharedArrayBuffer.

**Execution flow:**

```
Worker calls prompt(msg)
  → check pre-defined queue: if value available → return it immediately
  → else:
      self.postMessage({ type: 'input-request', message: msg })
      Atomics.wait(int32View, 0, 0)   ← blocks until state != 0
        (if state is already 1 when wait is called, returns 'not-equal' immediately — safe)

Main thread onmessage receives { type: 'input-request', message }
  → shows modal with message text
  → student types value, clicks OK (or presses Enter)
  → encodes value to UTF-8, writes bytes to buffer[8..], writes length to buffer[4..7]
  → Atomics.store(int32View, 0, 1)    ← set state = response ready
  → Atomics.notify(int32View, 0, 1)   ← wake worker

Worker resumes
  → reads length from buffer[4..7], reads bytes from buffer[8..]
  → decodes UTF-8 → returns string as prompt() result
  → Atomics.store(int32View, 0, 0)    ← reset state to idle
```

**`createBlocklyBlobWorker` new signature:**
```js
createBlocklyBlobWorker(jsCode, preDefinedInputs = [], sharedBuffer = null)
```
- `preDefinedInputs`: string array, consumed in order
- `sharedBuffer`: a `SharedArrayBuffer`; if null, interactive mode is disabled (prompt returns `''`)

## 3. UI Changes

### Student Practice Page (`BlocklyPracticePage.jsx`)

Layout (input controls shown only when `config.allowedBlocks` includes `text_prompt_ext`):

```
[ Exercise description            ]
[ Blockly workspace               ]
[ Python code view (if enabled)   ]

[ Input (one value per line):     ]   ← conditional
[ textarea (3 rows, monospace)    ]   ← conditional

[ Run ]  [ Hint ]          [ Export → ]
[ TLE warning / output panel      ]

[ Interactive input modal         ]   ← appears mid-run when queue exhausted
```

**Interactive modal:**
```
┌──────────────────────────────────┐
│  Enter input                     │
│  <prompt message from block>     │
│  ┌────────────────────────────┐  │
│  │ text field (autoFocus)     │  │
│  └────────────────────────────┘  │
│                        [ OK ]    │
└──────────────────────────────────┘
```
- No cancel/close button — student must submit a value to continue execution
- Enter key submits
- Modal is managed by React state (`inputModal: { open, message, resolve }`)

### Tutor Authoring Workspace (`BlocklyAuthoringWorkspace.jsx`)

Same textarea + modal added below the workspace and above the Run button, visible whenever `allowedBlocks` includes `text_prompt_ext`. Tutors use this to test their exercises with real inputs before publishing.

## 4. Error Handling

| Situation | Behaviour |
|---|---|
| `Atomics.wait()` not available (old browser) | Worker catches error, returns `''`, logs warning to console |
| Code calls `prompt()` more times than pre-defined inputs | Interactive modal appears for the remainder |
| Student submits empty string in modal | Valid — passed through as `''` |
| COOP/COEP headers break anything | No cross-origin assets in this deployment — no impact expected |
